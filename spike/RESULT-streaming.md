# 验证二：流式 Markdown 渲染实测报告

**结论：不需要容错解析器，架构不需要改。用现成 Markdown 库 + 每帧全量重渲染即可。**

真正的工程要点不在这里，而在**避免 O(n²) 的重复解析**（见第七节）。

---

## 一、要验证的问题

模型逐字吐出 Markdown，UI 每收到一个增量就重新渲染整条消息。担心的是：某些块级结构在「未闭合」和「已闭合」两种状态下渲染结果完全不同，闭合的瞬间整块内容重排，用户看到屏幕猛地跳一下。

## 二、度量方法

**指标：相邻两帧之间，上一帧有多少字符被作废。**

对每个前缀长度 n，渲染 `prefix(n)` 得到 HTML 帧。比较相邻两帧的公共前缀，`上一帧长度 − 公共前缀长度` 就是"抖动幅度"，单位是 HTML 字符数。

比较前先剥掉末尾的连续闭合标签（`</p>`、`</code></pre>` 等），否则"在末尾追加一个字符"会被误判成抖动。

**复现**：`NODE_PATH=<workspace>/node_modules node streaming_probe2.js` / `streaming_probe3.js`
**渲染器**：marked（真实库，非自研），文档 278 字符，含段落 / 代码围栏 / 表格 / 列表 / 链接。

## 三、第一问：渲染器对半截语法的真实行为

先问渲染器，不猜。

| 输入 | 渲染结果 | 判定 |
|---|---|---|
| `前文\n\n\`\`\`kotlin\nval a = 1`（围栏未闭合） | `<p>前文</p><pre><code>val a = 1</code></pre>` | **与闭合后完全一致** |
| 同上，补上闭合围栏 | `<p>前文</p><pre><code>val a = 1</code></pre>` | 无差异 → 零抖动 |
| `\| 参数 \| 默认值 \|`（只有表头） | `<p>\| 参数 \| 默认值 \|</p>` | 段落 |
| 补上分隔行 `\| --- \| --- \|` | `<table><thead><tr><th>参数</th>…` | **整块变表格** |
| `这是 \`一段代码`（未闭合） | `<p>这是 \`一段代码</p>` | 纯文本 |
| `这是 **重点`（未闭合） | `<p>这是 **重点</p>` | 纯文本 |
| `见 [官方文档](https://exa` | `<p>见 [官方文档](<a href="https://exa">https://exa</a></p>` | **URL 被自动链接化** |

**关键发现：未闭合的代码围栏不产生任何抖动**，marked 本来就把它渲染成 `<pre><code>`，闭合前后结果逐字节相同。

我原先的判断（"围栏代码块是最大的坑"）是错的。

## 四、第二问：抖动分布

| 方案 | 累计作废字符 | 单帧作废 > 20 字符的帧数 | 最严重单帧 |
|---|---|---|---|
| 朴素（每增量整段重渲染） | 853 | 8 / 278 | 66 字符 |
| 补全器（补围栏 / 补分隔行） | 2023 | — | 反而变差 |
| 尾部剥离（未闭合语法转纯文本） | 613 | 6 / 278 | 61 字符 |

朴素方案最严重的 8 帧，全部集中在两处：

- **链接区**（n=264~272，连续 8 帧）：`[官方文档](https://exa` 被 autolink，URL 每增长一个字符就重建一次 `<a>` 标签。这是**持续抖动**，占全部抖动的绝大部分。
- **表格分隔行到达时**（n=181）：表头行从段落变成 `<table>`，一次性 34 字符。

## 五、两个被否掉的方案

**补全器**（补上虚拟闭合围栏、补虚拟分隔行）：累计作废从 853 涨到 2023。因为它解决的是本来就不存在的问题（围栏），却给内容尾部引入了额外字符。

**尾部剥离**（把未闭合语法点之后的内容以纯文本渲染）：累计作废降到 613，但**单帧抖动数只从 8 降到 6**，且引入了新的中等抖动（n=166 / 169 / 236 处，40~61 字符）。

原因：`<span>` 纯文本尾巴与正常渲染之间的**切换本身就是一次重排**。这是把「持续小抖动」换成了「几次中等抖动」，属于指标优化陷阱。

## 六、真正的结论

**看每一处抖动的前一帧尾部，全都局限在最后 1~2 行，上方的已渲染内容从不跳动。**

原因是结构性的：唯一能「吞掉后续所有内容」的块级结构只有代码围栏，而渲染器对未闭合围栏的处理天然正确。表格和链接的重排都只影响自身所在行。

**所以：**

- 不需要容错解析器
- 不需要尾部缓冲
- 不需要维护有状态的流式渲染器
- 直接用现成 Markdown 库，每个增量重渲染整条消息

最坏情况（链接闭合）是约 66 字符的 HTML 变化，且局限在最后一行。**可接受，不值得为它增加复杂度。**

## 七、真正的工程要点：别让重渲染变成 O(n²)

虽然每次重渲染在语义上是正确的，但**每次都解析整条消息**会让总开销随消息长度平方增长：

一条 5,000 字符的回复 × 5,000 个增量 = 约 1,250 万字符的解析量。手机上会明显掉帧。

正确的做法是**按块缓存 + 只重渲染最后一块**：找出最后一个稳定块边界，边界之前逐块解析并缓存，之后只重渲染尾部。实测字符处理量降到 **26.3%**（`renderer_check.js`）。

但「按空行切块再拼接」不是无条件成立的。实测 8 个用例中**有 3 个产生了与整篇解析不同的 HTML**：

| 用例 | 整篇解析 | 逐块拼接 |
|---|---|---|
| `- 甲\n\n- 乙\n\n- 丙` | 一个 `<ul>`，三项都带 `<p>` | 两个 `<ul>`，第二项丢掉 `<p>` |
| `1. 甲\n\n2. 乙\n\n3. 丙` | 一个 `<ol>` | 两个 `<ol>`，第二个带 `start="3"` |
| 嵌套列表 + 空行 | 单个 `<ul>` 嵌套 | 拆成两个 `<ul>` |

原因：CommonMark 里**列表项之间允许有空行**（松散列表），空行并不结束列表。

修法：**追踪列表上下文，列表内一律不封块**。判断规则是——空行之后的非列表行，且缩进不深于列表起始缩进，才算列表结束。

另外两条同类规则：

- **围栏内部的空行不算边界**，否则代码块会被从中间劈开，前后两半各自独立解析，结果都不对
- **引用块**（`> a\n\n> b`）在 CommonMark 里本就是两个独立块，可以正常封块，实测一致

修正后 **13 个用例全部一致**，性能收益保持不变。

实现见 `android/StreamingMarkdownRenderer.kt`。

再叠加两个保护：

- **节流合并**：SSE 增量可能每秒几十个，按帧合并（约 16ms 一批）再触发渲染，而不是每个增量都渲染
- **尾部长度上限**：若整条回复是一个没有空行的超长段落，尾部会退化成整段。此时在最近的句末标点或换行处强制切分

## 八、复现方法

```bash
cd ai-chat-app/spike
NODE_PATH="<node-workspace>/node_modules" node streaming_probe.js    # 首版（假设错误，已被推翻）
NODE_PATH="<node-workspace>/node_modules" node streaming_probe2.js   # 半截语法真实行为 + 抖动定位
NODE_PATH="<node-workspace>/node_modules" node streaming_probe3.js   # 尾部剥离方案实测（已否决）
NODE_PATH="<node-workspace>/node_modules" node renderer_check.js     # 块缓存正确性 13 用例 + 性能收益
```

依赖：`marked`（`npm install marked`）。

**注意**：本报告用的是 marked。换成 markdown-it、commonmark-java 或 Markwon 后，个别行为可能不同（尤其 autolink 规则、表格识别、松散列表的 `<p>` 包裹），**换库后请重跑全部四个脚本**。度量脚本与渲染器解耦，替换 `render()` 即可；`renderer_check.js` 的 13 个用例就是用来兜这些差异的。
