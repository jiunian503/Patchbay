# 验证一：中文全文检索方案实测报告

**结论：采用「FTS4 + 汉字间插空格 + 短语查询」。这是唯一在中文场景下召回正确的方案，且 Room 原生支持。**

---

## 一、测试环境

| 项 | 值 |
|---|---|
| SQLite | 3.53.1 |
| ENABLE_FTS3 / FTS4 / FTS5 | 均可用 |
| 复现脚本 | `spike/fts_probe.py`、`spike/fts_probe2.py`、`spike/verify_cjktext.py` |

**注意**：上表是桌面 Python 内置 SQLite 的编译选项。Android 各厂商 ROM 内置的 SQLite 版本与编译选项并不一致，**必须在目标机型上跑 `CjkSearchInstrumentedTest` 才算最终通过**。

## 二、语料与查询

语料（5 条，模拟真实聊天记录）：

```
1  帮我把会议纪要整理成表格
2  会议纪要的模板放在哪里
3  今天天气不错，出去走走
4  我想做一个AI对话软件，类似RikkaHub
5  把上周的会议录音转成文字
```

期望值由 `LIKE '%q%'` 独立计算，不手写，避免测试自证。

## 三、方案对比

| 方案 | 「会议」 | 「会议纪要」 | 「RikkaHub」 | 可用性 |
|---|---|---|---|---|
| A. FTS5 默认分词器（unicode61），原文入库 | 无结果 | 无结果 | **无结果** | 不可用 |
| B. FTS5 + 汉字间插空格 + 短语查询 | `[1,2,5]` | `[1,2]` | `[4]` | 可用 |
| C. FTS5 trigram 分词器 | 无结果 | `[1,2]` | `[4]` | 不可用 |
| D. FTS4 默认分词器，原文入库 | 无结果 | 无结果 | 无结果 | 不可用 |
| **E. FTS4 + 汉字间插空格 + 短语查询** | **`[1,2,5]`** | **`[1,2]`** | **`[4]`** | **采用** |
| 基线. `LIKE '%q%'`（正确值） | `[1,2,5]` | `[1,2]` | `[4]` | 无索引，仅作对照 |

### 三个关键发现

**1. 默认分词器全军覆没，连英文都一起废掉。**

unicode61 把连续汉字视为单个 token，所以「帮我把会议纪要整理成表格」是**一个 token**。更严重的是「类似RikkaHub」——中文和英文之间没有空格，整串同样是一个 token，导致 `RikkaHub` 也搜不出来。也就是说：只要中文和英文挨着，英文查询也会静默失效。

**2. trigram 只能救 3 个字以上的查询。**

trigram 按 3 字符切分，因此「会议」「纪要」这类**两字词全部无结果**。中文里两字词占绝大多数，所以 trigram 在中文场景基本没用，不值得为它放弃兼容性。

**3. 插空格方案在 FTS4 上同样成立——这点最重要。**

Room 只原生支持 `@Fts4`；FTS5 需要手写建表 SQL，且依赖设备内置 SQLite 是否编译了 FTS5。既然 FTS4 已经能给出与 LIKE 完全一致的召回，就没有必要为了 FTS5 去冒机型兼容的风险。

## 四、已知语义差异（必须知情）

FTS 的多段查询是 **AND 语义**，不是子串语义。实测：

| 查询 | 构造的表达式 | FTS 结果 | LIKE 结果 |
|---|---|---|---|
| `对话AI` | `"对 话" ai` | `[4]` | `[]` |

原文是「我想做一个AI**对话**软件」，不存在连续子串「对话AI」。FTS 要求两个片段各自命中即可，于是召回了第 4 条。

**对搜索框来说这是更好的行为**（用户意图本就是找 AI 对话相关内容），但意味着 **FTS 召回是 LIKE 的超集**。若某处业务必须严格子串匹配，需在 Kotlin 侧对 `content` 再做一次 `contains` 过滤。

## 五、索引开销

| 项 | 值 |
|---|---|
| 原文合计字符数 | 68 |
| 插空格后字符数 | 123（**1.81x**） |
| FTS5 索引体积 | 24,576 字节 |
| FTS4 索引体积 | 28,672 字节 |

文本膨胀 1.81 倍，索引体积两者同量级（样本太小，仅说明无数量级差异）。聊天记录文本量下完全可以接受；若未来要索引附件全文，需重新评估。

## 六、bm25 排序观察

查询「会议」，三条命中记录的 bm25 得分全部为 `-0.0000`，**无区分度**。

原因：样本仅 5 条，词项出现在 3 条文档中，IDF 退化。这不足以否定 bm25，但足以说明：**不要过早依赖它**。当前实现按 `created_at` 倒序返回，等真实数据量上来、确认 bm25 有区分度后再换。

## 七、FTS5 额外能力（若将来切换到 FTS5）

在方案 B 的切分基础上，FTS5 额外支持：

| 能力 | 表达式 | 实测结果 |
|---|---|---|
| 拉丁前缀 | `rikka*` | `[4]` |
| 多词 OR | `"会 议" OR "录 音"` | `[1,2,5]` |
| 多词 AND | `"会 议" AND "纪 要"` | `[1,2]` |
| NEAR 邻近 | `NEAR("会 议" "纪 要", 4)` | `[1,2]` |

FTS4 同样支持前缀与布尔运算，NEAR 语法略有差异。

## 八、落地要点

1. **入库与查询必须用同一套切分。** 只切一边等于没切。
2. **FTS 表里的文本是索引文本，不能拿去显示。** 展示时用 rowid JOIN 主表取原始 `content`（见 `MessageFtsDao.search`）。
3. **主表与 FTS 表必须同事务写入。** Room 不会自动同步，主表删了消息而 FTS 表没删，检索结果里会出现幽灵记录。
4. **用户输入不能直接拼进 MATCH。** `"`、`-`、`*` 都是 FTS 语法字符，必须走 `CjkText.forQuery()`。
5. **空查询串要短路。** 把空串传给 MATCH 会让 SQLite 抛异常。
6. **不要用 `fallbackToDestructiveMigration()`。** 用户填的是自己的 API Key、攒的是自己的聊天记录，清库等于灾难。
7. **不要用 FTS 的 `snippet()` / `highlight()`。** 索引文本里插了空格，高亮结果会变成「会 议 纪 要」。正确做法是在原始文本上自己做高亮。

## 九、复现方法

```bash
cd ai-chat-app/spike
python fts_probe.py        # 方案 A~D 与 LIKE 基线对比
python fts_probe2.py       # FTS4 验证、前缀/布尔/NEAR、索引开销
python verify_cjktext.py   # CjkText 逻辑端到端验证（12 用例）
```

真机验证：

```bash
./gradlew connectedDebugAndroidTest   # 跑 CjkSearchInstrumentedTest
```

**必须跑通真机测试再往下写业务代码。** 桌面 SQLite 的行为不能代表目标机型。
